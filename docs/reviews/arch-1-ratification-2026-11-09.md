## 2. Rulings

**R-1. The platform rule by job class: APPROVED, with one amendment to the shape test (F-3).** Only a `local` job is run by the launcher, so only a `local` job has a ran file, a job-image platform in `linux/amd64|arm64` and an image id; the always-on, `ci-only` and `content` jobs' verdicts run on the runner, and their records name the runner's platform and `image none`. Reason: the class is not the writer's choice but the workflow fence's, since W-7 holds every `local` job's verdict to `container run` and every `ci-only` job's to `bash <adapter> <job>` (kit/README.md:91), so the record says where the verdict actually ran. Rests on DESIGN §5.2's row "for any other job, whose verdict runs on the runner itself, the runner's" and §6.5's `platform` row. The amendment: the plan's shape test for the other classes (`^[a-z0-9]+/[a-z0-9_]+$`, kit/lib/keys.sh:618) must accept every string `kit_platform_of` can write on a runner the kit admits, or say in its sentence that the shape is wrong; today a `uname -s` holding `-` or `.` is written and then refused as "records no platform". Now stated in DESIGN §5.2 (the paragraph "The job's class decides where its platform comes from").

**R-2. MINOR.** "The plan's sentences" in CONTRIBUTING.md:83 and "a predicate sentence" in kit/README.md §5.1 mean the DECISION SEMANTICS an adopter's workflow reads: a decision value, an existing output's name or meaning, and the outcome of a trust test on a record an earlier release wrote. A note's human text, a new column and a new output are not among them. Reason: MAJOR is defined by "an adopter must act" (CONTRIBUTING.md:83), and nothing a conforming adopter wrote to v1.1.0 changes meaning: every earlier record is decided as before (claims 8 and 9), the existing outputs keep their names and values, and the new refusals (return code 3) apply only to a record shape no earlier release wrote. One narrowing is real and is named instead of hidden: `<job>_platform` is now reserved, so a plan extension that wrote such a name fails red. The example has no extension, so it is listed as a check in the entry's actions, not an act. The CHANGELOG's first line now says this. kit/README.md §5.1 carries the definition. CONTRIBUTING.md:83 is outside this review's documents and should say the same (F-2).

**R-3. The live proof is the example's re-vendor pull request of `v1.2.0-rc.1`. The fallback name is `ci-green-<job>-<key>`, held ready, not built.** Reason: the kit repository's own workflow writes no records (its `.github/workflows/ci.yml` runs `tests/run` and `tests/image` only), so the example's `checks` job, whose record step runs on every pull-request run, makes the first real `POST git/tags`. A release candidate exists for exactly this kind of fact (CONTRIBUTING.md, "How a release is cut"; today's precedent). The same run proves the second unknown in the same request: the body sends no `tagger`, and GitHub must accept that from the job token. Neither the trust check nor the pruner reads the tag's name or its tagger: `kit__green_facts` reads the header's `type` and `object` and the message (kit/lib/keys.sh:594-599), and `prune` ages by `*committerdate`. So a fallback changes one string in `kit/bin/record`:146 and moves no record's trust.

If the run fails, the record step exits 1 (kit/bin/record:149-152), so the job goes red after its tests passed. That is visible, and no record is written wrong. The order is then: no `v1.2.0`; a fix piece changes the name to `ci-green-<job>-<key>` (one path component, accepted by any refname rule, no `/`), or adds a `tagger` of `github-actions[bot]` if the refusal names the tagger; `v1.2.0-rc.2` is tagged; the example re-vendors and runs. The read-back to check on the first green run is `git cat-file tag <the ref>` in a fresh clone: the header names the commit, the message is the facts block byte for byte, and no signature tail was added. The reader tolerates such a tail anyway, because it looks names up exactly once each. DESIGN §5.2 now says that no reader reads the name and where its acceptance is proven.

**R-4. An expected difference, not a silent skip.** The eleven are the AC-KI-27 cases of `init_guard` (kit/tests/fam/init.sh:713-760). That guard is a step of the kit repository's own workflow, read out of `../.github/workflows/ci.yml`, and a vendored or image-copied `kit/` has no such file beside it. Claim 11 shows it: 540 cases become 529, and claim 10 shows 1,415 become 1,404 with no `NOT RUN` line. Reason: DESIGN §6.10's `NOT RUN <leg>` is for a leg that CANNOT run where it should, and the driver refuses to record a job whose log names an unlisted leg. This guard does not apply in an adopter's tree at all, and an adopter's kit job must print no `NOT RUN` line (kit/README.md §6.1), so it prints one plain line saying it does not apply. The precedent is recorded: docs/kit-init.md:104 traced the same 11 (1,269 against 1,258) at v1.1.0. The difference is visible, constant and pre-existing, and this piece did not introduce it.

**R-5. Confirmed. The platform admits nothing.** A green record is admitted on the recomputed key and the check run alone (DESIGN §5.4 tests 1 and 3). The facts test (2) can only refuse, turning a skip into a run, and a branch can sidestep it entirely by writing a lightweight record, which is still trusted. Reason: on a pull-request run the branch controls the writing job (DESIGN §3.1, §3.4), so its facts are its own statement, worth exactly what the check run is worth. The piece changes no admission: `kit__green_facts` returns before the check-run call on disagreement (kit/lib/keys.sh:566-567), and its success only sets `KIT_RECORD_PLATFORM`. DESIGN §3.1 already said "believed as far as the check run is and no further". §5.4 now says it where the rule lives (the paragraph "What the platform decides").

**R-6. Sound.** The lifecycle is tight: `container run` removes the key's ran file before the job starts (kit/bin/container:584), writes it only after exit 0 and a readable platform (kit/bin/container:674-686), and `record` refuses with exit 2 before any request when it is absent or malformed. The path is sound in CI: `--git-common-dir` of the job's own checkout, written and read in the same job by steps W-7 fixes in order, and a GitHub-hosted job's checkout is fresh, so no other run's file can be read. Reason: the ran file is evidence of WHERE, never of WHETHER. The pass is the record step's place under `if: success()`, which W-4 holds (kit/bin/check-workflow:422-423), and the file adds a guard of its own: a verdict step made to continue past a failure leaves no file, so `record` refuses. Two residues, both notes: a self-hosted runner with a persistent workspace plus a launcher refusal before line 584 plus `continue-on-error` could read a stale file, but the file names only a platform and an image, so the worst outcome is a stale platform on a record whose check run is real; and workstation runs leave ran files that nothing prunes (F-6).

**R-7. Nothing presumes step 2's shape.** The checks: the platform is in no key, no ref name and no ref namespace; the green format is `-green v1`, so a target line can come with a v2; trust still decides one record per job per key; the Linux-only test for a `local` job's green record restates the local arm's existing rule (DESIGN §6.5, §6.7 condition 2's neighbour) for today's container-only `local` class and will move with that class; `kit_platform_of` already spells a non-container target (`openbsd/amd64`) in the same shape the plan accepts for non-`local` jobs. Reason: each of these is a place step 2 may change without undoing anything here. The one interface step 2 inherits is the `<job>_platform` output. It is one value per job, which step 2 may want to reshape, so DESIGN §5.3 step 8 now calls it informational: no decision of the kit reads it, and it carries only what the writing job said.
