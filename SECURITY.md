# Security

## Reporting a vulnerability

Please report it privately, through GitHub's private vulnerability reporting on this repository: open the **Security** tab and choose **Report a vulnerability**. Please don't open a public issue or pull request for it.

Tell us which release or commit you looked at, what an attacker would need (push rights, a listed signing key, a workstation running their commit, a crafted manifest) and what they would gain (a job skipped that should have run, code vendored that was never released, a secret reaching a container). The most useful report of all is a test case that fails against the current code.

## What the kit promises

The kit decides whether a CI job may be skipped because the exact files it depends on have already passed. Its promises are narrow, and they are set out in full here so that you can repeat them in your own documentation.

- **A record is a listed key asserting that a set of files passed.** A local record proves that the holder of a key in the signers file on your protected `main` branch said the tests passed. It does not prove that the tests ran, or that they ran in the job image. The kit makes a false record hard to produce by accident and limits what a deliberate one can achieve: signing is only possible after the job's own script has exited 0; the plan refuses a record whose tools were off their pinned versions, whose counts are zero, which skipped an unlisted test leg, or which has been moved to a different set of files; the signers file and the allow-list are read from `main`, never from the branch (a branch's manifest can only choose which file on `main` is read as the signers file, so on a pull-request run, where the branch already controls the plan, it could point at another listed file on `main` such as `ci/KIT-SIGNERS`, but it cannot add a key); and the weekly scheduled run re-tests the tip of `main` on CI, ignoring every local record.
- **The checks on CI's own records catch accidents, not deliberate abuse.** A CI green record is trusted when its key can be recomputed from its commit and that commit has a successful check run for the job from `github-actions`. On a pull-request run, the workflow, the plan and the trust check all come from the branch itself, so anyone with push rights could already skip a job by editing them. On a public repository that includes anyone who opens a pull request from a fork: the fork's workflow runs its own plan, so green checks on a fork pull request that touches `ci/` or `.github/` prove nothing, and a reviewer should read those files before trusting the checks. A fork's token is read-only, so it cannot write a record. A green record is a convenience for honest runs, not a security boundary.
- **Nothing protects you from a malicious commit that you run through `make check`, the hook, `kit-update` or the check commands.** Those run on your workstation as you, and the commit's own code runs there too: its key library in a child shell, its dependency install, its tests. Run `kit-update` from a checkout of `main`, never from a branch someone else wrote, and think before running `make check` on a contributor's branch on a machine that holds a listed signing key. The risk outlives the run: the workstation's cache volumes (`<project>-ci-gomod`, `<project>-ci-gobuild`, `<project>-ci-npm`) are written by the job and shared by every later run on that machine, so one poisoned run can taint later records until you remove the three volumes with `docker volume rm`. CI's caches are per run, and unaffected.
- **Jobs without the Docker socket run with limited reach**, which protects you against code the commit's author did not write: test code, modules and packages run in a container with an allow-listed environment, no SSH agent, no home directory, no clone, no new privileges and no capabilities. Git inside the container has no credential helper, and any push to `https://github.com/`, `git@github.com:` or `ssh://git@github.com/` is redirected to a path that cannot exist. The container keeps ordinary network access (its own network when the job has a service, Docker's default bridge otherwise), so code inside it can still reach GitHub by other means; what it lacks is any credential the kit handed it, because the environment allow-list refuses every runner variable and every name that looks like a token, key, secret, password or credential. A job that is given the socket (the manifest's `socket` line) has no such limits: it can start containers that mount whatever Docker can reach, which on a desktop VM includes your home directory, and on the runner it could write a green record for any key.
- **The manifest is data, and cannot shape a shell on the host.** One awk program parses it; it is never sourced or evaluated, and no word in it can act as a glob, an option or a pattern.
- **A kit update vendors a release, not merely a signed object.** `kit-update` accepts a tag only when its own name, type and message say it is a release of this kit, its commit is on this repository's `main`, and it verifies against the `ci/KIT-SIGNERS` on your own `main`. The first time you vendor, when your `main` has no such file yet, it verifies against your working copy's file and prints each line's fingerprint for you to confirm against the one published in [README.md](README.md) before you commit it.

The design, every control and the reason for it, is in [DESIGN.md](DESIGN.md) §3. The paragraph to copy into your own documentation is §3.4.

## Review history

The kit was reviewed for security before its first release candidate. The review made fourteen findings (one high, two medium, eleven low). Each was either fixed, with a test case that fails without the fix, or accepted and written down as a limit. The fixes are the controls DESIGN.md and [kit/README.md](kit/README.md) now describe, among them the release check in `kit-update`, the shapes a path or option may take in the manifest, the reserved names for jobs, tools, counts and environment variables, the pinned actions and bounded permissions the workflow check requires, and the hardened job containers.
