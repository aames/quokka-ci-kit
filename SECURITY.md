# Security

## Reporting a vulnerability

Please report it privately through GitHub's private vulnerability reporting on this repository: the **Security** tab, then **Report a vulnerability**. Do not open a public issue or pull request for it.

Say which release or commit you looked at, what an attacker needs (push rights, a listed signing key, a workstation running their commit, a crafted manifest), and what they gain (a job skipped that should have run, code vendored that was never released, a secret reaching a container). A planted case that turns red is the most useful report of all.

## What the kit promises

The kit decides whether a CI job may be skipped because its exact content already passed. Its promises are narrow, and stated here in full so you can repeat them in your own documentation:

- **A record is a listed key asserting that a tree passed.** A local record proves that the holder of a key in the signers file on your protected `main` said the tree passed. It does not prove the tests ran, or ran in the job image. The kit makes a false assertion hard to produce by accident and bounds what a deliberate one can reach: signing is reachable only after the job's own script exited 0; the plan refuses an off-pin tool, a run that counted nothing, an unlisted skipped leg and a record moved to another tree; the signers file's contents and the allow-list come from `main`, never the branch (the branch's manifest chooses only which file on `main` is read as the signers file, so on a pull-request run, where the branch already controls the plan, a branch could name another listed file on `main` such as `ci/KIT-SIGNERS`; it cannot add a key); the weekly scheduled run re-tests `main`'s tip on CI and ignores every local record.
- **The green arm catches accidents, not malice.** A CI green record is trusted when its key recomputes from its commit and that commit has a successful check run of the job from `github-actions`. On a pull-request run the workflow, the plan and the trust function are the branch's own, so anyone with push rights can already skip a job by editing them. On a public repository that includes anyone who opens a pull request from a fork: the fork's workflow runs its own plan, so green checks on a fork pull request that touches `ci/` or `.github/` prove nothing, and a reviewer reads those files before trusting the checks. A fork's token is read-only, so it cannot write a record. A green record is a convenience for honest runs, not a boundary.
- **Nothing is isolated from a malicious commit run through `make check`, the hook, `kit-update` or the check commands.** Those run on your workstation as you, and the commit's own code runs there too (its key library in a child shell, its dependency install, its tests). Run `kit-update` from a checkout of `main`, never from a branch someone else wrote, and think before running `make check` on a contributor's branch on a machine that holds a listed signing key. That risk outlives the run: the workstation's cache volumes (`<project>-ci-gomod`, `<project>-ci-gobuild`, `<project>-ci-npm`) are written by the job and shared by every later run on that machine, so one poisoned run can taint later records until you remove the three volumes with `docker volume rm`. CI's caches are per run and not affected.
- **Jobs without the Docker socket are narrowed against code the commit's author did not write**: test code, modules and packages run in a container with an allow-listed environment, no SSH agent, no home directory, no clone, no new privileges and no capabilities. Git inside it has no credential helper, and its pushes to `https://github.com/`, `git@github.com:` and `ssh://git@github.com/` are redirected to a path that cannot exist. The container keeps ordinary network access (a job with a service on a network of its own, any other on Docker's default bridge), so code in it can still reach GitHub by other means; what it lacks is a credential the kit handed it, because the environment allow-list refuses every runner name and every name shaped like a token, key, secret, password or credential. A job given the socket (the manifest's `socket` line) is not narrowed: it can start containers that mount whatever Docker can reach, which on a desktop VM includes your home directory, and on the runner it could write a green record for any key.
- **The manifest is data that cannot shape a host shell.** It is parsed by one awk program, never sourced or evaluated; no word in it can be a glob, an option or a pattern.
- **A kit update vendors a release, not merely a signed object.** `kit-update` accepts a tag only when its own name, type and message say it is a release of this kit, its commit is on this repository's `main`, and it verifies against the `ci/KIT-SIGNERS` your own `main` carries; at your first vendoring, when `main` carries none, it verifies against your working copy's file and prints each line's fingerprint for you to confirm against the one published in [README.md](README.md) before you commit it.

The design, every control and the reason for it, is [DESIGN.md](DESIGN.md) §3; the residual paragraph to copy into your documentation is §3.4.

## Review history

The kit was reviewed for security before its first release candidate. The review made fourteen findings (one high, two medium, eleven low); each was fixed, with a planted test case that turns red without the fix, or accepted and stated as a limit. The fixes are the controls DESIGN.md and [kit/README.md](kit/README.md) now describe, among them the release binding in `kit-update`, the path and option shapes in the manifest, the reserved names for jobs, tools, counts and environment variables, the pinned actions and bounded permissions in the workflow fence, and the hardened job containers.
